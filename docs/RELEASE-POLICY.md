# PLIUM · 独立版本与发布制度

> 状态：2026-11-16 建立；适用于 `ardss/PLIUM`。本文是**交付流程**，不表示首版已经发行。重要：构建包 ≠ 发布版本 ≠ Windows A 安装验收。

## 1. 产品身份与版本

- 产品：**PLIUM / 叠间**，独立维护；上游 Edge-Drop 只作为 Apache-2.0 开源技术来源，选择性同步正收益，不同步上游版本号。
- 保留安装身份 `com.ardss.plium`、`PLIUM.exe`、用户数据目录 `%APPDATA%\plium`。改版本号不能迁移、清空或重新初始化真实历史。
- 旧版 `0.4.0-plium.10` 只属于**历史内部预览系列**；没有签名、公开稳定发行或有效在线更新通道。
- 首个**独立**候选版本预计命名 `1.0.0-beta.1`（候选，非已发布）：特意高于已安装的 `0.4.0-plium.10`，避免把 `0.1.0-beta.1` 当作 Windows/NSIS 版本降级。正式确定版本前必须先做安装/升级/回滚验证。
- 独立稳定发行须另行经过签名、真实设备验收与用户 GO；`1.0.0-beta.1` 不等于 `1.0.0` 稳定版。
- 版本/标签/资产一一对应：`plium-vX.Y.Z[-beta.N]` → 唯一源码 SHA、校验和、候选报告、安装包、回滚包；禁止同名覆盖、强推标签、替换已公开二进制文件。

## 2. 开发与发布彻底解耦

1. **DEV（随时）**：Windows B 的功能分支开发、测试、审查；小改动可以频繁提交或运行，不改版本号、不推送安装给 Windows A。
2. **INTEGRATION（集成）**：单一 `main`，通过 PR、静态检查、全量测试及安全审计收敛；CI 可以构建未签名安装程序以验证包装，但一律 `--publish never`，**不代表对外发布**。
3. **RC（同一发布里程碑）**：冻结首版范围，列出 blocker 和 SHA，B 机隔离原生 GUI 及压力测试；只有阻塞类回归/数据安全问题才允许进入该里程碑，完成一组修复后生成新的不可变候选构建。
4. **Windows A 验收**：建立完整私有资料备份，记录安装包 SHA-256；安装后核对数据库前后哈希/历史记录、真实交互、托盘、原生拖拽、双屏/不同缩放、重启自启、焦点、异常日志。**同一台机器仅一套常驻 PLIUM**。保留上一可回退安装包，不同时运行两个剪贴板监听器。
5. **GO / 发布**：所有适用门禁有实际证据、用户确认交付、发布说明明确兼容与回滚。未经合法签名和公开发布门禁，不发布宣称为稳定版的安装包、不打开自动更新。
6. **STABLE（后续）**：仅在已发布候选持续使用且无阻塞回归、签名及所有公共发布门禁通过后升级为稳定。

## 3. 发布节奏（解决反复发版）

- 以**两周一次/可用里程碑**作为常规对外发布窗口；没完成门禁就顺延，不为了日期强发。
- **一个发布里程碑只维护一个集成队列**；日常修复只提交代码。严禁因每个图标、微动效、文案变化就重新命名并安装一个用户版。
- 每次候选版至少完成 B 机全量 CI、安全检查、关键真实 UI 交互、Windows A 交付验证，并连续使用观察一段时间。首个独立候选建议观察 48 小时；用户可在问题可复现且修复证据充分时调整，但不能跳过数据安全门禁。
- 紧急安全漏洞、数据丢失、无法使用的 P0 可走**热修复通道**，仍要有独立测试、来源 SHA、备份和回滚证明。
- 新功能按 **P0（阻塞安全/核心可用）→ P1（候选交付条件）→ Next（下一期价值）** 分类；新想法先记录，不自动扩大当前 RC 交付面。
- 变更摘要/QA 状态一次性汇总，只有**可用版本、明显阻塞或需要用户介入**才通知用户，避免“做一点报告一点、发一点包一点”。

## 4. 非谈判式发布门禁与证据

| 门禁 | 必须留存的真实证据 |
| --- | --- |
| 代码/安全 | 具体 Git SHA；CI 通过；全部测试；官方 npm audit；无未经审核的来源/更新地址 |
| 发布身份 | 项目名 / AppID / profile 路径一致；package-lock 版本一致；版本大于现有已安装版本（实际 NSIS 验证） |
| 数据 | Windows A 完整备份（加密索引、图片、Local State）；前后 SHA-256 与记录内容验证；回退工件已保存 |
| 原生体验 | 一行↔三行；边缘呼出；托盘；筛选、搜索、清除确认；文本/图片/文件拖拽；双屏/DPI；焦点；冷启动 |
| 交付 | Windows B 构建 SHA、安装包 SHA、Windows A 安装/运行版，三者可对账；独立 QA 和用户可验收 |
| 公开稳定版 | 证书与 Authenticode 验证、SmartScreen 风险与分发说明、Git 历史安全审计、语言/RTL 适用范围、支持与回滚指引 |

未经签名可制作**本地/内部 QA 包**，但不得误称已签名公开稳定版。首次独立 Beta 的公开范围和免责说明应独立审批。

## 5. 经验复盘：为什么原来节奏不合理

- **错误一：以构建次数代替产品进度。** 多次 `.8/.9/.10` 混用了修复、CI 和 Windows A 安装；以后开发提交次数与可安装版本次数分开记录。
- **错误二：遗漏完整链条。** `git commit`、CI 绿、NSIS 构建、A 安装、真人验证是五个不同状态，不能用前一个替代后一个。
- **错误三：缺冻结线。** UI 优化、品牌、功能与事故修复夹在一起，导致补丁无限追加；以后 RC 开始后只接 P0/阻塞回归，下一期另记。
- **错误四：跨设备验证不对齐。** B 上用合成数据通过并不等于 A 上真实多显示器/拖拽/重启可用；以后 B 自动化 + A 真实交互缺一不可。
- **错误五：上游与我们的版本混淆。** Fork 源码可复用，产品身份、版本、标签、发布权限、更新源必须完全自主。
- **错误六：误以为已验证就不会出问题。** 2026-11-16 A 的 `AppHangTransient` 表明偶发主线程问题不会被简单单测排除；需要真实故障证据、最小修复、压力测试与使用观察。
- **错误七：过多临时脚本和报告。** 将验证方法和最终证据绑定到唯一里程碑目录，保留审计记录，但不为每个小尝试建立新产品发布。
- **正确实践：** 像 2026-11-09 的 undici 崩溃一样先复现、用合成数据建立回归、再 QA/安装保留历史；避免把“未复现”说成“根因已修复”。
